# ADR 0001: Resolve OpenVINO symbols explicitly, not with `dynlib`

Status: accepted, 2026-09-24.

Applies to every module under `src/openvino/raw/`.

## Context

Nim offers two ways to call a shared library.

The `{.dynlib.}` pragma is the concise option. One pragma per procedure, no
loader code, and the declaration reads almost exactly like the C prototype,
which is what an auditable ABI layer wants.

The development plan also requires diagnostics that `dynlib` cannot deliver:

- Section 9.1 requires an `OpenVinoLibraryError` exception for a missing
  library or a missing required symbol.
- Checklist item C13 requires an actionable diagnostic when either is
  missing.
- Section 8.5 requires that diagnostic to name the target platform, the
  library names that were tried, the expected OpenVINO version and a hint
  about installation or loader configuration.
- Section 12.3 requires a clear error on a major/minor mismatch rather than
  a crash at some later, arbitrary call.

## Measurement

A minimal program declared one procedure against a library that does not
exist, then printed a line *before* calling it:

```nim
proc missingFunction(): cint {.cdecl, dynlib: "definitely_absent_lib.dll",
                               importc: "definitely_absent_symbol".}

echo "reached main body"
try:
  echo missingFunction()
except CatchableError as err:
  echo "caught: ", err.msg
```

Result on Windows with Nim 2.2.12:

```text
could not load: definitely_absent_lib.dll
RUN_EXIT=1
```

`reached main body` never printed. Nim loads `dynlib` libraries during module
initialisation, and on failure writes one line to stderr and calls `quit(1)`.
The `try` block is unreachable.

## Decision

The raw layer resolves symbols explicitly through `std/dynlib`:
`loadLib` for the library and `symAddr` for each entry point, behind a single
loader module.

Loading is lazy and happens on first use, not at module initialisation, so a
program that merely imports the package still starts.

## Consequences

Accepted costs:

- Each bound function needs a procedure-pointer type, a cached pointer and a
  forwarding procedure, instead of a single pragma. The pattern is mechanical
  and is generated by one documented template so that the function name and
  its signature still appear together on one line, diffable against the
  header.
- A forwarding call adds one indirection and one nil check. This is
  negligible next to the inference work the call performs, and the plan
  forbids optimising before a benchmark exists.

Gains beyond the requirements above:

- Missing library and missing symbol become the same catchable failure with
  the same diagnostic.
- The required-symbol test (checklist item C15) and the Phase 2 gate check
  that the `_props` entry points resolve are natural uses of the loader
  rather than separate machinery.
- The compile-time library name override stays a single string in one module,
  satisfying section 8.5 without touching any declaration.

## Narrow exception to "the raw layer raises nothing"

Plan section 4.1 states that the raw layer must not raise Nim exceptions.
The loader is a deliberate, documented exception, limited to one failure mode:
the library or a required symbol could not be resolved.

The reason is that there is nothing to return. Every bound function reports
failure through `ov_status_e`, but a call that never happened has no status.
Reusing `GENERAL_ERROR` would merge "OpenVINO is not installed" with
"OpenVINO rejected your arguments", which is exactly the diagnostic collapse
that sections 8.5 and 12.3 exist to prevent.

The exception stays narrow in three ways. It covers load and symbol
resolution only, never a status code. It is raised from one module rather
than from the bound declarations. And every bound function continues to
return `ov_status_e` unchanged, so the rule still holds for all normal
operation.

## Explicitly not decided here

How the managed layer maps a status code to an exception, and how handles
express ownership. Those are separate records.
